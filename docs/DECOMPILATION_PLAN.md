The canonical tree follows Digimon World 2's structure: `src/<module>/`, `include/`, `asm/us/<module>/`, `config/us/`, `config/us/linkers/`, and `tools/`. The current sector-derived source slots preserve layout; they are not proven original translation units. The native Windows PSY-Q build retains file-specific compiler and assembler reproduction settings from the old repository. Byte identity does not establish original object boundaries or compiler provenance; those need the separate review described in `CODEGEN_MODEL.md`.

`analysis/pre-migration/20261007-canonical-import` preserves the earlier small WSL-based C build. `analysis/legacy-audit/20261007T124110254143Z/project` preserves the independently verified old snapshot. Neither reference is edited during decompilation. The canonical source tree is the editable working project.

## Work order

1. Integrate the complete verified older tree and preserve all newer verified game functions. Correct known code mistakenly classified as data. Establish a fresh canonical 14-module gate with input fingerprints.
2. Exclude proven SDK entries from game progress and restore SDK C to symbolized assembly. Review library/data relocations and identify ambiguous movie routines separately.
3. Recover remaining game functions by module and source slot. Prefer adjacent functions sharing object layouts. Use unverified m2c drafts as hints; retain assembly fallback after unsuccessful candidates and record the reason in `config/us/worklist.json`.
4. Reconstruct types and interfaces for archive loading, module loading, object lifetime and adjusted dispatch, resource management, game state, rendering, audio use, and each stage. Name only behavior established by code and callers.
5. Review all non-`func` game manifest entries. The splitter's `asm` or `data` label can hide compiled game code; a percentage based only on current `func` rows does not settle this review.
6. Replace opaque game data with typed tables/structures where understood. Record asset inclusions and pointer relocations; keep opaque assets supplied from the user's disc.
7. Validate movable sections and cross-overlay references, then modified builds and runtime behavior. Matching bytes alone do not prove a safe modding build.

Completion requires no unresolved compiled-game assembly placeholders, a reviewed inventory of genuine handwritten code and SDK, readable types/interfaces, complete verified outputs, and documented data/relocation limitations. We will not call the project complete merely because all binaries build or a provisional counter reaches 100%.
